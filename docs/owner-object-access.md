# Owner object access

This first slice authorizes computers and retro terminals (`computer.use`) and their authored linked neon sign effects (`neon.power`, `neon.configure`). Vehicles, doors and other future objects are outside this scope.

WorldProject may declare `objectAccess: {schema: "elsemesh.object-access/1", rules: [{objectId, actions: ["computer.use"]}]}`. An explicit empty rule array denies every object action. Unknown actions, mismatched kinds, duplicate IDs and malformed policy reject admission. Retro terminals use their referenced `terminal.objectId`, never the terminal record ID. Absent policy alone derives the installed supported computer, retro and neon declarations; the panel displays **Legacy world defaults**. The normalized policy has version 1 and a SHA-256 digest including its compatibility mode.

The authored rule is a ceiling. Every playing browser identity, including an owner administrator, needs an explicit private player/object/action grant. Current generic VIEW and ENTER policy also applies. Administrator status permits managing grants, never implicit computer use. The accepted authority pose must be within three metres (or the smaller terminal radius) of the effective object world transform; hidden objects and hidden ancestor subtrees deny interaction. A computer may affect only its authored targetSignId. Computer use plus the target sign action must both be granted in the same SQLite transaction that applies an effect.

## Explicit administrator provisioning

Use the existing private owner setup state and an already enrolled browser node:

```
node tools/networking/owner-world-setup.mjs delegate-admin --state-dir /private/owner-state --player-node elsemesh-node:<browser-public-node-hash>
```

This reads the existing owner key, signs a content/world/authority/epoch/browser delegation, and writes private object-admin-delegations.json beside the checkpoint. Restart the owner runtime to load the delegation. It expires with content admission. No browser, localhost or repository access is inferred to be administration. No owner key is exported or generated by this command.

## Browser protocol

The existing signed owner browser envelope carries these operations: object-access-read, object-access-update, object-use, object-neon-power, object-neon-configure and object-overlay-read. Payloads bind worldId, contentDigest, sessionId, generation, policyDigest and policyRevision. Initial access-read can omit policy digest/revision to discover the current context. Every other call requires the exact current values. Clients send a unique accessRequestId in addition to the signed transport requestId.

Grant updates add expectedRevision, playerNodeId, objectId, action and allowed. A stale revision rejects without mutation. Use adds objectId. Neon effects add objectId (the computer), targetObjectId and value (boolean power) or config (validated complete neon configuration).

Results are authority signed elsemesh.object-access-result/1 envelopes binding requestId, accessRequestId, operation, player, active session/generation, world/content, authority epoch, effective policy digest/version/revision and issuedAt/expiresAt. Results expire after three seconds. Normal denied actions return allowed:false with **Access restricted**. The client renews computer use each second and closes use on lease expiry, denial or session change. Shared effects perform fresh current checks per request and do not trust a cached use lease.

Access read returns isAdmin, policyMode, rules, own grants, effectiveActions (own grants intersected with the authored ceiling and generic ENTER permission) and private gameplay overlay. Administrators additionally receive enrolled labels and all grants. Grant access read and management require ACTIVE local membership. The separate object-overlay-read operation requires an authenticated current VIEW session and returns only the overlay, permitting destination portal previews without exposing private grant lists.

## Private persistence and limits

Grants, policy revision, bounded audit, operation replay records and neon overlay live in the existing private SQLite authority ledger transaction. They never modify authored Git content. Grants bind the content digest and effective policy digest; changed context clears prior grants and overlays and increments revision. Replays are checked both by the browser runtime and within the transaction. Audit retains the most recent 4096 updates. Restart preserves the ledger grants, revocations and overlay.

Focused Node tests cover absent/empty/malformed policies, administrator versus visitor, private delegation tampering, explicit use grants, coarse permission intersection, wrong session generation/reference/action, replay, distance and authored links, revocation, and SQLite restart persistence. These tests provide server evidence; physical browser interaction is a separate acceptance gate.


## Review corrections

Authority delegation, content admission and grant expiry are checked at execution
inside the serialized ledger transaction. A queued request cannot reuse authority
that expired while it waited.

The C64 interpreter yields to browser tasks during long programs and checks the
current use authorization while running. Closing/revoking cancels running and
queued execution. Reopening keeps editable program source, with fresh interpreter
memory and execution state; old variables and CONT state are not retained.

Native Access/F1/terminal and welcome audio acceptance are separate from the
source tests. Portal-preview sign overlay refresh remains unimplemented; active
world overlay updates are supported. This slice introduces computer and linked
neon actions only, not boat or helicopter authority.
