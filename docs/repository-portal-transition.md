# Repository portal transition

RepositoryFederation is the only membership ledger. FederatedWorldTransition is the client transfer state machine. RepositoryPortalTransition adapts the installed PortalTransport and RepositoryWorldHost preparation/activation boundaries.

Call createRepositoryPortalTransition({transport,host,portal,sourceActive,load,descriptor?,getAppearance?,onFrozen,onStatus}). load(descriptor) must verify owner signatures, pinned content digest and admission. The result exposes transition, travel({signal}), frozen, reservation, recover(), cancel(). Do not run overlapping attempts or replace an unresolved transition. onFrozen suspends input and pose simulation, and outgoing normal poses are suppressed by transport. The adapter waits for a signed accepted crossing receipt before requesting a reservation, prepares destination assets at the reserved pose, marks resources ready, obtains the signed handoff, then commits membership. Only a committed authoritative pose activates the prepared scene.

Cancellation and failures before handoff cancel any reservation before resuming input. A commit acknowledgement loss queries status; if both fail, the transition stays outcome-unknown with input and outgoing poses frozen. recover() queries the same reservation and either activates committed membership or resumes only after authoritative cancellation/expiry. Activation failures also stay frozen for recovery. Do not resume input in an unconditional finally block.

The additive elsemesh.handoff/2 signature binds the proof-key node, destination authority and destination session. Independent destination admission binds source session, destination session, player and region; a valid source signature alone cannot admit entry. Legacy /1 exports are unchanged.

Authored portals use radians with local +Z as front; legacy federation transforms use degrees and the opposite crossing direction. The bridge uses entry yaw = authored source yaw in degrees + 180 (normalized) and exit yaw = authored destination yaw in degrees. This represents the authored implicit half-turn. Owner invitation and acceptance proofs must be regenerated with repositoryFederationPortal; changing authored geometry or signing legacy raw radians invalidates the approved descriptor. Private operator configuration is regenerated by its existing local generator; keys and enrolments remain private.

Focused validation: node --test test/federation.mjs test/federation-v2.mjs test/repository-federation.mjs test/repository-world-server.mjs test/repository-portal-transition.mjs. Browser and physical device evidence remain separate acceptance criteria.

Personal avatar appearance uses the existing AvatarAppearance validator and browser key elsemesh.avatar.v1. Both normal poses and signed accepted crossing receipts include the five allowlisted appearance fields. The authenticated membership ledger validates appearance before accepting a state, publishes it in presence/welcome, and retains it through transfers and reconnects. Appearance is personal session state, never authored repository content or an identity key; arbitrary asset URLs and additional fields are rejected.

## Disconnected transfer recovery

Keep the existing transition and its reservation when the coordinator socket closes. While controls remain frozen, call await transport.reconnectForRecovery(), then await attempt.recover(). Reauthentication reuses the exact browser proof-key identity and does not open a scene or unfreeze input. It validates the welcome against the previously pinned source/destination content, authority, world, session and membership generation, and adopts the authority's next pose sequence. The subsequent ledger query must identify this node and the same reservation/source generation. Activation uses the committed pose only after that validation; definitive cancellation or expiry permits source resumption only in the original source session. A signed accepted crossing calls getAppearance() at transfer time; supply the persistent in-memory AvatarChooser value so personal appearance survives fresh destination Player instances when browser storage is unavailable. Its default uses the active player profile, then browser storage.

Recovery is bounded by the in-memory coordinator ledger: disconnected membership retention is approximately 30 seconds and reservation retention approximately 75 seconds from preparation. If membership has expired and reauthentication creates a new session, an older committed reservation must not activate its old pose or resume source controls. The runtime remains frozen and reports unsupported/expired recovery. Coordinator restart persistence is not implemented.
